# External Models → Procedural World

## Production direction

This is a library pipeline, not a one-off prefab-import workflow. A future
production asset must move through the same contract regardless of whether it
was made in Blender, generated by another tool, or revised later.

The goal is that adding the hundredth model is no more structurally expensive
than adding the first:

```text
Source asset package
    -> authored LOD export
    -> Unity import and prefab assembly
    -> automated validation
    -> approved archetype catalog entry
    -> streamed presentation
```

Generation, save data, and networking continue to use only stable archetype
IDs. They must never depend on an FBX path, a prefab instance ID, or a current
LOD level.

## Asset family contract

Every model belongs to an asset family. A family is identified by one stable
`ArchetypeId`, such as `tree_main_01` or `rock_ground_01`, and may have many
visual variants.

- The archetype describes gameplay/generation meaning and placement rules.
- A variant changes only presentation: mesh, materials, authored LODs, and
  optional harmless visual detail.
- A new generation rule needs a new archetype; a prettier replacement does
  not.
- Variant selection remains deterministic from `WorldSpawnData.stableId`.

This prevents visual-library growth from creating a matching growth in
generation rules, saves, or multiplayer state.

## Responsibilities

### Local/external script

Your separate modeling project owns:

- model creation;
- geometry cleanup;
- polygon optimization;
- export;
- optional textures/material preparation;
- copying the finished model into the Unity project's Ready folder.

### Unity

Unity imports the finished export, creates a local prefab and LODGroup from
authored LOD nodes, maps known texture names to Little Castle shader families,
and registers the prefab as a local visual variant. Mesh reduction and source
art editing remain outside Unity.

## Folder contract

External script target:

```text
Assets/_Game/Models/Ready/<Category>/<ArchetypeId>/<VariantFile>
```

The category folder is organizational.

The `ArchetypeId` folder is important because the current generator already
creates logical objects by archetype ID.

Example:

```text
Assets/_Game/Models/Ready/Trees/tree_main_01/
├─ Tree01.fbx
├─ Tree02.fbx
├─ Tree03.fbx
└─ Tree04.fbx
```

All four become visual variants of `tree_main_01`.

The same generated tree keeps the same variant after chunk unload/reload
because `WorldSpawnCatalog` selects variants from the object's stable ID.

The folder contains *Unity-ready exports*, not a source-art archive. Keep
`.blend` files, high-poly sources, raw scans, and intermediate baking output in
the chosen external art library or Git LFS only after an explicit storage
decision. Do not silently put a large source-art library into normal Git.

The current local-library paths are Git-ignored:

```text
Assets/_Game/Art/Source/       # Blender/source/baking data
Assets/_Game/Models/Ready/     # Unity-ready model exports
Assets/_Game/Textures/Ready/   # Unity-ready texture exports
```

Their Unity `.meta` files are ignored too. They must therefore arrive through
the same external sync as the assets themselves. Never commit a versioned
catalog or prefab that references an ignored asset; it will be missing for
every clone that has not synchronised the local library.

## Blender/source export contract

The modelling workflow should use a reusable Blender scene/template and export
profile rather than hand-configuring each model.

Every export intended for the Ready folder must meet these rules:

1. Units are metres; object scale is applied and transforms are clean.
2. Pivot/origin is intentionally placed for world placement (normally ground
   contact at local zero); forward direction is consistent across the library.
3. Names are stable and descriptive: `ArchetypeId_Variant_LOD0`, etc. Names
   must not rely on Blender's automatic numeric suffixes for identity.
4. Materials are assigned by the Little Castle object family, not by a unique
   ad-hoc shader for every model.
5. Major world models include authored LOD0, LOD1, LOD2, and a far silhouette
   tier when their visible scale warrants it. Geometry must decrease by LOD.
6. The far tier has no realtime shadows, local lights, or detailed colliders.
7. Collision geometry is separate, simple, and present only for asset families
   that need near-gameplay collision.
8. Foliage exports keep trunk/branches separate from leaves, or carry the
   required Vertex Color R wind mask. See the foliage preflight before export.
9. Texture maps follow the material/texture contract and are exported at a
   justified resolution; world textures require mipmaps after Unity import.

The Blender template should contain named collections for render LODs and
collider meshes, plus an export script/preset that can batch-export selected
families. Creating the script is a future tooling task; the required output
contract is deliberately fixed now so it can be automated without changing the
runtime.

## Unity assembly contract

Unity receives an export, then creates one reviewed prefab variant:

```text
Ready export
  -> prefab variant
  -> LODGroup + shared Little Castle materials
  -> optional near-only collider / managed emitter
  -> WorldSpawnCatalog[ArchetypeId]
```

Prefab assembly must not create `renderer.material` clones or unique runtime
materials. Repeated objects reuse shared materials, GPU instancing where
compatible, and `MaterialPropertyBlock` only for small per-instance variation.

The catalog remains the only mapping between an archetype and its visual
variants. Replacing a variant there is safe for deterministic world data,
provided the archetype's footprint and gameplay meaning did not change.

### Local preview and build boundary

`Little Castle -> Assets -> Sync Ready Models` creates local LOD prefabs and
updates an ignored `LocalWorldSpawnCatalog` under `Models/Ready`. In the Unity
Editor, this catalog overrides only the matching entries in the versioned
`MainWorldSpawnCatalog`. Shared placeholder entries remain intact. The overlay
is Editor-only; standalone builds currently use the shared placeholders.

Before shipping production visuals, define how the external asset library is
versioned, delivered and included in reproducible builds. Do not rely on an
unrecorded local folder for release builds.

## Current intake commands

The external asset library has a `manifest.json` (schema example:
`Tools/asset-library-manifest.example.json`). Its `Exports/` folder holds FBX
and textures; Blender source stays outside the Unity project.

```powershell
python Tools/asset_sync.py --library "E:\\Little-Castle-AssetLibrary"
python Tools/asset_sync.py --library "E:\\Little-Castle-AssetLibrary" --apply
```

The first command checks paths, types, duplicates, missing files and planned
changes without copying. The second copies changed files atomically, preserves
existing `.meta` files and never removes stale files. Review the printed plan
before applying. The library location is an example; the tool accepts any
explicit path.

Each FBX variant must have nonempty `LOD0`, `LOD1`, `LOD2` sibling nodes and
may have `LOD3`. Each later LOD must have fewer vertices, and all visual
renderers must belong to exactly one LOD node. Unity assembles a local prefab
and LODGroup; violations reject the model. Far-LOD shadows and probes are
disabled. Collider meshes and gameplay collision tiers are not assembled by
this first intake tool; those need category-specific rules before production
approval.
Texture names are `<Variant>_<Family>_<Map>` with families `Solid`, `Leaves`
or `Grass`, and maps `BaseColor`, `Normal`, `AO`, `Roughness`, `Opacity`.
`<Variant>_BaseColor` is also accepted for a single solid material. Imported
textures receive mipmaps and their map-specific color-space setting.

Run `Little Castle -> World -> Sync Models And Generate Preview` after Unity
imports the copied files. The command can make a local test scene preview, but
it does not certify a production asset. Run both model and foliage validators
where applicable, then inspect close/far appearance and frame cost.

## Admission gate

An asset is not production-ready merely because it appears in the scene. Before
it may replace a placeholder or be added to `WorldSpawnCatalog`, record a PASS
from these checks:

1. **Source check:** export contract, scale, pivot, naming, LODs, material-map
   inputs, and required collision intent are present.
2. **Unity importer check:** textures are correctly typed/compressed, mipmaps
   are enabled for world textures, and CPU Read/Write is off unless justified.
3. **Prefab check:** run `Little Castle -> Assets -> Validate Selected
   Production Model`; resolve errors and document intentional warnings.
4. **Foliage check:** for every tree/plant, run `Little Castle -> Rendering ->
   Foliage -> Validate Selected Model` and inspect close/far Play Mode wind and
   shadows.
5. **World check:** place the variant through the real `WorldSpawnCatalog`,
   test chunk unload/reload, and inspect day, sunset, and night at strategy
   camera distances.
6. **Budget check:** profile a representative dense chunk. Check spawn
   presentation time, draw calls/batches, memory, LOD transitions, and collider
   count against the current streaming baseline.

No asset should bypass the gate simply because it is visually attractive. A
single problematic prefab is fixed at the asset/prefab level before shared
streaming or shader architecture is made more expensive.

## Scaling the library

Use two presentation paths, selected by asset family and measured density:

| Family / density | Initial presentation | Production evolution |
|---|---|---|
| Landmarks, buildings, rare resources | Prefab variants | pooled roots; authored distant/HLOD representation |
| Trees, rocks, repeated props | Prefab variants at low/medium density | grouped GPU-instanced presenter by mesh/material/LOD |
| Grass and dense foliage | never one GameObject per blade | dedicated instanced/cluster presentation |
| Distant forests and villages | individual lower LODs initially | authored clusters/HLOD silhouettes |

Both paths consume the same `WorldSpawnData` and catalog identity. The choice
of a presentation backend is transient: it is not saved, replicated, or used
by authoritative generation.

## Automation roadmap

Implement tooling in this order, after the contract has been exercised with a
small representative set of real assets:

1. Blender export preset/script that validates naming, transforms and expected
   LOD collections before copying exports into `Ready`.
2. Unity `AssetPostprocessor`/import preset for model and texture defaults.
3. Catalog synchronizer that discovers valid Ready families, reports missing
   or duplicate variants, and proposes catalog updates without silently
   changing gameplay mappings.
4. Batch validator that emits a compact report for all changed asset families
   in CI or before a release.
5. Measured instanced presenters, pooling, and HLOD generation for the
   families that dominate profiler cost.

Do not automate automatic mesh decimation as the default production path.
Author LODs where silhouette and material choices can be controlled.

## Tomorrow's fastest iteration loop

```text
1. Make/export several models
2. Local script copies them into Ready folders
3. Let Unity import them
4. Run Little Castle > World > Sync Models And Generate Preview
5. Inspect scale, density, repetition and composition
6. Adjust models or generation settings
7. Repeat
```

Textures are optional for this stage.

Untextured models are enough to evaluate:

- silhouette;
- object scale;
- tree density;
- rock density;
- visual repetition;
- spacing;
- landmark readability;
- how well the procedural world composition works.

## Important

Do not create one procedural archetype per visual variant unless the models need
different spawn rules.

Usually:

```text
one archetype
+
many visual variants
```

is preferable.

The admission gate and automation roadmap above replace this former
open-ended extension list. Implement automation against the stable contract,
not as per-model exceptions.
