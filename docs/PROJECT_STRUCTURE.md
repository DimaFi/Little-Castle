# Project Structure

The Git repository root is also the **Unity project root**.

Do not create a nested second Unity project unless this document is intentionally changed.

```text
Little-Castle/
├─ Assets/                 Unity assets and game code
│  └─ _Game/               Everything authored specifically for Little Castle
│     ├─ Scripts/
│     ├─ Art/               Project art; Art/Source is local and Git-ignored
│     ├─ Models/Ready/      Local Unity-ready model library; Git-ignored
│     ├─ Textures/Ready/    Local Unity-ready texture library; Git-ignored
│     ├─ Prefabs/           Future prefabs
│     ├─ Materials/         Future materials
│     ├─ Scenes/            Future scenes
│     └─ Settings/          Future project ScriptableObject assets
├─ Packages/               Unity package manifest (generated when Unity project is created)
├─ ProjectSettings/        Unity project settings (generated by Unity)
├─ docs/                   Technical documentation for developers and AI agents
│  ├─ architecture/
│  ├─ decisions/
│  ├─ gameplay/
│  └─ workflows/
├─ Tools/                  Future non-runtime developer tooling
├─ README.md
└─ AGENTS.md
```

## Important separation

### Google Docs
Use Google Docs as the human-editable **Game Design Bible**:
- lore;
- gameplay concepts;
- rules;
- progression;
- economy design;
- narrative;
- brainstorming;
- approved design decisions.

### GitHub / docs
Use repository documentation for information needed to safely work on the codebase:
- architecture;
- data contracts;
- implementation rules;
- setup;
- workflows;
- technical decisions;
- subsystem integration notes.

### Unity Assets
Only runtime/editor assets required by the Unity project belong under `Assets/`.

## Rule: no duplicate Unity project

The correct future setup is:

```text
Git clone
   ↓
Little-Castle/              <- open this folder in Unity Hub
   ├─ Assets/
   ├─ Packages/
   └─ ProjectSettings/
```

Never create `Little-Castle/UnityProject/Assets` unless the entire repository layout is deliberately migrated.

## Third-party assets

When third-party Unity packages/assets are introduced, keep project-owned content under `Assets/_Game/`.

Do not edit third-party package files unless unavoidable.

## Large binary files

Large source art, Blender files, videos and raw production files should not be added casually to the main Git history.

Before committing large binary assets, decide whether they belong in:
- Unity source control;
- Git LFS;
- shared Drive storage;
- an external asset library.

Document that decision first.

### Local production-art library

The current decision is that high-volume source art and locally imported
production models/textures do **not** enter normal Git history. The following
paths are intentionally Git-ignored, including their Unity `.meta` files:

```text
Assets/_Game/Art/Source/
Assets/_Game/Models/Ready/
Assets/_Game/Textures/Ready/
```

`Assets/_Game/Models/Ready/README.md` is the one tracked exception: it keeps
the folder contract visible in a clean clone.

These files must be supplied through a separately agreed asset-library sync
(for example a shared external drive, cloud asset library, or later Git LFS
workflow). A clone without that sync is valid for code work but cannot preview
or build production visuals that rely on the local library.

Do not commit a `WorldSpawnCatalog` or other versioned Unity asset that holds
references to files from these ignored folders. Such references become missing
on a clean clone. The Ready model synchronizer writes an ignored
`LocalWorldSpawnCatalog` for Unity Editor previews; the shared catalog keeps
its placeholders. The current local overlay is not included in standalone
builds. A production build needs an explicit asset delivery and build pipeline.
